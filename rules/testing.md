# テスト規約

**基本方針: 古典学派(Classicist / Detroit School)でテストを書く。**

実例（NG/OK・過去に踏んだ形）は [`harness/case-law/testing.md`](../harness/case-law/testing.md)。
迷ったときと、指摘を受けたときに読む。

## 配置と命名

テストは対象モジュールのフォルダ内の `__tests__/` に置く。

命名規則: `{テスト対象ファイル}.{カテゴリ}.test.<拡張子>`

- カテゴリはテストの観点を表すラベル(`normal` = 正常系 / `edge` = 境界値・異常系 / 特定の仕様領域)
- **グルーピング構文のネストの代わりにカテゴリ(=ファイル)で分割する**。1ファイルが肥大化したらカテゴリを分けること

## 古典学派のテスト

2本柱は「**何をテストするか = 振る舞い**」と「**依存をどう扱うか = 実物を使う**」。

### 1. 振る舞い(仕様)をテストする

テストは**外から観測できる振る舞い**に対して書く。実装の内部構造に対して書かない。

- テスト対象は公開APIの「入力 → 出力/最終状態」のみ。内部のヘルパー関数・中間データ構造・処理順序はテストしない
- テスト名は**仕様の文として**書く(「○○のとき□□になる」)。関数名・実装語彙ではなくドメイン語彙を使う
- 1テスト1振る舞い。複数の仕様を1つのテストで検証しない
- **リファクタリング耐性を判断基準にする**: 振る舞いを変えずに実装を書き換えたときに壊れるテストは、実装詳細をテストしている証拠なので書き直す
- テストケースの根拠は仕様・設計ドキュメントに求める。仕様にない振る舞いをテストで固定しない
- **API を作り替えるときは、既存テストの観点を先に数える。** 型名やメソッド名を変えると既存のテストファイルが丸ごと動かなくなるが、そこにある観点(dangling 参照・循環・定義順・空など)は仕様であって、書き換えの都合で消えてよいものではない。**新しく思いついたケースだけを並べた一覧は、たいてい元より薄い**

### assert は「落ちうるか」と「1つの仕様か」で見る

テスト名が仕様の文になっていても、assert がその仕様を捉えていないことがある。書いたあとに次の2つを確かめる。

**1. その assert は落ちうるか。** 入力にその情報が存在しない状態で「出ない」ことを確かめても、実装が何をしても通る。

判断の仕方: **その assert を通すために実装をどう壊せるかを考える。** 壊し方が思いつかないなら、そのテストは何も守っていない。

- **既定値・フォールバックがある処理では、既定値と違う答えになる入力を選ぶ。** 「規則で決まる答え」と「既定値」が同じ入力を使うと、規則を丸ごと壊しても既定値のほうで通ってしまう
- **「空になる」を確かめるテストには、同じ入力の中に集まる側を1件置く。** 対照を1件置き、期待値を「その1件だけの並び」にすると、集める側を壊しても集めすぎる側を壊しても落ちる
- **「出さない」を確かめるときは、入力から自明にならない側を見る。** 0 件のときに行が無いのは入力から決まるので、行の数を見ても実装を守れない。守りたいのが「0 件なら枠を出さない」なら、枠そのものを見る
- **不在の照会が `null` になる理由が2通り以上あるなら、その assert は守っていない。** 絞り込みの条件を重ねた照会は、**条件が外れたのか、対象そのものが消えたのか**を区別しない。対象を存在前提の照会で引いてから、外れてほしい側だけを見る
- **落ちるか迷ったら、その1件だけ実装を壊して走らせる。** 疑わしい assert 1 つのために分岐を消して 1 ファイル回すだけなら数秒で済む。頭で判断せず確かめる

**2. 1つの assert が複数の仕様を固定していないか。** 表示全体を文字列として比べると、テスト名が指していない仕様まで巻き込む。関係のない変更で落ちるため、リファクタリング耐性が下がる。

### 2. モックは原則使わない

依存は実物を使い、相互作用(呼び出し回数・引数)ではなく**結果の状態・戻り値を検証**する。

- 純粋なロジックのテストでモック・スタブ・スパイの使用は**全面禁止**(実物で検証できるはず。モックが必要に感じたら設計を見直す)
- 例外として代替してよいのは**プロセス外・制御不能な境界のみ**: 外部 I/O(ネットワーク、ファイルシステム、時刻、乱数)。この場合もモックライブラリによる自動モックより、テスト用の単純な実装(フェイク)を優先する
- モジュール丸ごとの差し替えは禁止
- 内部実装の呼び出し検証は外部境界の検証以外で使用しない

## テストの書き方: ネスト禁止

Kent C. Dodds の "Avoid Nesting when you're Testing" に従う。

- グルーピング構文のネストは禁止(ファイル直下にテストをフラットに並べる。グルーピングが必要ならカテゴリファイルを分ける)
- 前処理フックでの変数共有・ミューテーションは禁止。テストに必要なセットアップは**各テスト内に書く**か、セットアップ関数(`setup()`, ファクトリ)を呼び出す
- テストは1つだけ読めば前提がすべて分かる状態にする
- クリーンアップが必要な場合のみ後処理フックを許可(リソース解放など、テストの理解に影響しないもの)

## テスト用ヘルパーの置き場所

**テストに書こうとしているヘルパーが汎用の操作なら、それは実装側に足りていない機能。** テストファイルにその場しのぎで書かず、実装側へ置く。

- 判断軸: そのヘルパーは**テストであることに依存しているか**。表明はテスト固有だが、「値を取り出す」「オブジェクトを組み立てる」は汎用操作なので実装側に置く
- **移す前に、その assert がそのヘルパーを必要としていること自体を疑う。** ヘルパーが表示のための綴りを組み立てているなら、実装側へ移すと表示の知識がドメインへ入る。多くの場合テストが見たいのは綴りではなく**構造**で、構造のまま比べればヘルパーごと要らなくなる
- 同じヘルパーを2つ以上のテストファイルに書いたら、その時点で共通化する(実装側へ移せるならそちらを優先)
- テスト固有のセットアップ(ファクトリ・`setup()`)は各テストから呼ぶ形で共有してよい
