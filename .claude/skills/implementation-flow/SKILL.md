# 実装フロー

実装は次の 8 フェーズを順に通る。**フェーズを飛ばさない。** 飛ばすと決めたなら、
飛ばした理由を Issue に書く。種類のファイル(「作業の種類」)がフェーズを置き換える・
無くすのは、飛ばすことに当たらない(理由はそのファイルが持つ)。

| # | フェーズ | 出力 |
| --- | --- | --- |
| 1 | ゴールの確定 | Issue に書かれたゴール |
| 2 | タスクの分割 | 必要なら分離した Issue |
| 3 | 計画 | Issue に書かれた計画と却下案 |
| 4 | 計画の検証 | `plan-reviewer` の指摘と、それへの対応 |
| 5 | 実装 | コードとテスト |
| 6 | 実装の検証 | `implementation-reviewer` の指摘と、それへの対応 |
| 7 | PR | 差分と判断を説明する PR |
| 8 | マージ後の追記 | 閉じた Issue へのコメントと、続きの Issue |

**検証の観点はこのファイルに書かない。** `.claude/agents/plan-reviewer.md` と
`.claude/agents/implementation-reviewer.md` が持つ。観点を親のコンテキストへ通さないための分割。

## 作業の種類

**作業の種類は Issue の `flow:*` ラベルで決まる。** 種類ごとの手順は**種類のファイル**が持ち、
このファイルの各フェーズに足す・置き換える。決め方はフェーズ 1「種類の確定」。

| ラベル | 種類のファイル | 変わるフェーズ |
| --- | --- | --- |
| `flow:feature` | [`feature.md`](feature.md) | 3 / 5 / 6 / 7 に足す |
| `flow:bugfix` | [`bugfix.md`](bugfix.md) | 1 / 3 / 5 / 6 / 7 に足す |
| `flow:refactor` | [`refactor.md`](refactor.md) | 3 / 5 / 6 に足す |
| `flow:investigation` | [`investigation.md`](investigation.md) | 1 に足し、3 / 4 / 8 を置き換え、5〜7 は無い |

**検証を軽くする種類は作らない。** どの種類も計画(investigation では調査)の検証を省かない。
小さな作業向けに検証を省く種類を作ると、「役割の分担」が捨てた「修正の小ささ」の線引きが
種類の選び方に入り込む。

## 役割の分担

**親セッションは指示役で、計画も実装も自分では書かない。** 計画は `planner`、実装と採用した指摘の
修正は `implementer` が担う。親のコンテキストに調査の過程と差分の書きかけを積まず、採否と記録の
判断だけを残すための分割。

| フェーズ | 担当 |
| --- | --- |
| 1 ゴールの確定 / 2 タスクの分割 | 親 |
| 3 計画 | `planner`。返ってきた計画を親が Issue へ書く |
| 4 計画の検証 | 親が `plan-reviewer` へ渡し、採否を決める。直しは `planner` へ戻す |
| 5 実装 | `implementer` |
| 6 実装の検証 | 親が `implementation-reviewer` へ渡し、採否を決める。直しは `implementer` へ戻す |
| 7 PR / 8 マージ後 | 親(push 前検査・commit・push・PR・Issue への追記) |

- **親はリポジトリの中のファイルを編集しない**(ソースに限らず `.claude/` `harness/` `rules/` も)。
  修正の小ささは理由にしない(1 行でも `implementer` に渡す)。線引きを毎回判断すると分担が崩れる
  (→ `.claude/hooks/block-parent-session-edit.sh`)
- 親が作業ツリーを変えてよいのは、判断を伴わない次の 2 つだけ
  - 整形などの自動修正コマンドをフェーズ 7 で走らせる
  - 検証エージェントの書き換えを、基準のコミットへ `git restore` / `git clean` で戻す
    (「サブエージェントの使い方」)
- Issue・PR 本文を書くのは親。`planner` / `implementer` / `investigator` は返すだけ
- この分担は `implementation-flow` の中だけで、`harness-record` / `harness-growth` には及ばない

## フェーズ 1: ゴールの確定

**「何ができるようになれば終わりか」を 1〜3 行で書く。** 実装手段ではなく達成状態で書く
(「`EditHistory` を作る」ではなく「編集を戻せるようになる」)。

- ゴールが決まらないなら、決まらない理由(仕様の欠落 / 選択肢が割れている)を先に潰す。
  曖昧なまま計画に進むと、計画の検証が「何と照らすか」を持てない
- **自分で潰せず回答を待つなら、そこで止める**。選択肢と根拠を Issue へ書き、
  **作業中のセッションの URL を併記する**(`rules/process.md`)。推測で埋めて計画へ進まない
- 対応する Issue が無ければ**先に作る**。Issue 無しで実装を始めない(判断の置き場所が無くなる)
  - 自分で進める Issue には、作成の呼び出しでも後からでも assignee を付けない(理由は `rules/process.md`
    「Issue に紐づいて起動したら、セッションの URL を Issue に残す」)。フェーズ 2 で分けた Issue のうち、
    このセッションで続けて進めるものも同じ
- 仕様の拠り所は設計ドキュメント。このリポジトリにはまだ `docs/` が無いので、拠り所は
  `rules/`、過去の実例は `harness/case-law/`
- ゴールの書き方は `.github/ISSUE_TEMPLATE/implementation.yml` と `.github/ISSUE_TEMPLATE/epic.yml` の
  ゴール欄にも写してある。変えたら揃える

### 種類の確定

ゴールと一緒に作業の種類(「作業の種類」)を決める。**ラベルは人が決める。** 分類用の
ラベル(`bug` / `enhancement` など)があっても、種類は決めない。

1. Issue の `flow:*` ラベルを読む

   ```bash
   gh api 'repos/{owner}/{repo}/issues/<番号>' --jq '[.labels[].name | select(startswith("flow:"))]'
   ```

2. 表にある値が 1 つなら、それが種類。着手のコメントに種類を書く
3. 0 個 / 2 つ以上 / 表に無い値なら、親が提案する種類と根拠を添えて人に尋ねる
   - 対話中なら AskUserQuestion で尋ね、**人が答えた種類のラベル**を親が付ける
     (`gh api -X POST 'repos/{owner}/{repo}/issues/<番号>/labels' -f 'labels[]=<人が答えたラベル>'`。
     `<人が答えたラベル>` は `flow:bugfix` のようにラベル全体)。
     2 つ以上・表に無い値を外すのも、人が答えたときだけ
   - 人がいない起動(Issue の assign から起動した等)なら、提案と根拠をセッションの URL と一緒に
     Issue に書いて止める
4. Issue を作るときは、**作成の呼び出しの中で**種類を決める(作った後でラベルを付ける形は、忘れても
   何も止まらない)。行の書式は `.claude/hooks/lib/issue-flow-kind-violations.py` の定数が持ち、欠けた
   作成は `block-issue-without-flow-kind.sh` が止める(止めた理由に書式が出る)
   - (a) 対話中なら AskUserQuestion で尋ね、人が答えた `flow:*` を作成の呼び出しのラベルに含める
   - (b) 人がいない起動なら、本文に提案の行を書く
   - (c) `implementation-flow` に通さない Issue(`harness-growth` の介入・棚卸し・Epic など)は、本文に
     通さない行を書く。Epic なら、作成の呼び出しのラベルに `epic` も含める
5. **親が自分で選んだ `flow:*` ラベルは付けない・外さない。** 親は種類を提案するまでで、決めるのは人。
   選ぶ側と手順が軽くなって得をする側が同じだと軽い側へ倒れる(`implementation-flow` を通さず
   検証エージェントだけを呼んだ実例が `harness/case-law/process.md`「単発（まだ語彙にしていない）」の
   pr-473 にある)。「無ければ `flow:feature`」のような既定値も同じ理由で置かない(ラベルの無い
   Issue でバグ修正の再現テストが抜ける)
6. 途中で種類が変わったら、ここへ戻って確定し直し、フェーズ 3 から計画し直す。古い種類のまま
   検証した計画は使わない。種類に合わない作業だと分かったときも、3 の手順で人に尋ねる

## フェーズ 2: タスクの分割

`rules/process.md`「タスクの分割」に従う。判断軸は「**独立してマージできるか**」。
片方だけ入っても壊れない単位が 2 つ以上見えたら Issue を分ける。

分けた / 分けなかったのどちらも判断なので、理由を Issue に残す。分けた側の Issue の種類は、
フェーズ 1「種類の確定」の 4 で決める。

## フェーズ 3: 計画

**`planner` に立てさせ、返ってきた計画を親が Issue に追記する。** 渡すもの:

```text
ゴール: <ゴール>
Issue: #<番号>
種類: <`flow:*` のラベル>
分割の判断: <分けた / 分けなかった理由と、スコープ外にしたもの>
```

計画に書くのは次の 4 つ。

1. **変更するファイルと、そこに何を置くか。**
   行の単位で直す記述があるなら「何行目のどの記述をどう直すか」まで書く。
   **公開 API を変える場合は、それを呼んでいるテスト・サンプルも変更するファイルとして
   数える**(数え漏らすと、検査が落ちる状態で計画が固まる)。
   **列挙・分岐へ枝を足す場合も同じく数える**(枝を足しても既存のテスト・検査は落ちないので、
   数え漏らしても誰も教えてくれない)
2. **テストケースの一覧。** 仕様の文(「◯◯のとき□□になる」)で書く(`rules/testing.md`)
3. **却下した案と、やめた理由**
4. **未決の判断。** 無いなら「無し」と、各セクションを洗った結果を 1 行で書く

却下案を残すのは、後で同じ案が再浮上したときに前回の理由が失われるため。
「A にした」だけでは、B を試していないのか、試して駄目だったのかが読めない。

### 計画を渡す前に踏む 8 つの手順

判断ではなく**毎回同じ順で踏む段取り**で、順番を間違えると意味が変わる(呼び出し側を数える前に
テストを書き始めると、後から型が通らなくなる)。実例は
[`harness/case-law/planning.md`](../../../harness/case-law/planning.md)。

1. **消す/変える公開 API があれば、呼び出し側を grep で数える。**
   `grep -rn "\.<名前>\b"` / `grep -rn "<消す名前>"` で本番コード・テスト・サンプルを
   数え、計画のファイル表に挙げる。計画が `harness/case-law/README.md`「判例の外の文書を変えたとき」に
   当たるなら、判例に残る写し・参照も数えてファイル表に挙げる。ファイル表で見落としやすいもの
   (コードの参照を grep しても出ないもの)と探し方は、
   `harness/case-law/planning.md`「`plan-file-omission`」「`plan-comment-reference`」に当てて数える
2. **一括置換・複数箇所の書き換えを伴う計画は、立てた収集条件を実際にコードへ当てて件数を
   検算する。** 「`const` 宣言を集める」「◯◯という語を置換する」のような条件を文章のまま
   計画に書かない。`grep` / 実際のスクリプトを走らせて出てきた件数と、計画が前提にしていた
   件数(呼び出し側の依存・書き換えが要る既存テストの数、モジュール表へ併記する実体の列挙を
   含む)が一致するかを、**項目を 1 つずつ**突き合わせて確認する
   (`分類: plan-scope-count-verification`)
3. **想定した接続先・前提・検証手段が実例で本当に成立する/機能するかを確認する。**
   既存ヘルパー・retarget 先の fixture が想定通り動くか、「A なら B」という前提が実際の
   コード・実行結果で崩れていないかを、読むだけで済ませず実際に動かして確かめる。
   **検証コマンド自体が意図した範囲を覆っているか**(ディレクトリの深さ・拡張子の指定漏れ・
   `git mv` 後は `diff` に出ない・表記ゆれで grep が対象を拾えない、で一部しか見ていない、を
   含む)も同じ手順で確かめる。**この種の前提・接続先の主張を計画に書いたら、書き終える
   たびに `claim-verification` スキルで確かめる**(フェーズ5だけでなく、計画を書くこの
   フェーズでも呼ぶ。plan-reviewer に渡してから手戻りする形が pr-352 以降 7 件続き、
   すり抜けは 0(毎回レビューで捕まる)なのに計画の書き直しが繰り返されたため、
   `plan-reviewer` へ渡す前に確かめる位置へ前倒しした。`分類: plan-scope-premise-verification`)
4. **テストケースが前提とするヘルパー・フィクスチャ・API が実在し、想定通り動くかを確認する。**
   既存のヘルパーを流用する計画なら、そのヘルパーが確かめたい経路へ実際に到達できるかを
   コードを読んで確認する(到達できないなら、その場で計画を直す)
5. **却下案に書いた理由が事実を主張しているなら、その事実を実際に開いて/`grep` して
   確かめてから書く。** 「`rules/` に既にある」「このフィールドがあるから
   代入できる」のような理由は、確かめずに書くと結論は合っていても理由が事実と食い違う
   ことがある。確かめた結果と食い違ったら理由の側を実物に合わせて書き直す
   (`分類: plan-rejection-reasoning`)
6. **却下する案について、似た構造の実装が既にコードに無いかを `grep -rn` 等で探す。**
   見つかったら却下案の一覧へ候補として足す。見つからなければ「探したが無い」と計画に書く。
   探さずに「他に無い」という前提で却下しない(`分類: plan-rejection-coverage`)
7. **触るモジュール・呼び出し元の doc / Why コメントが「常に◯◯である」「〜のときのみ」と
   書いている前提を、この計画が崩さないか `grep -rn` で確かめる。** 崩すなら、崩れる `@returns` /
   不変条件を計画(ファイル表・テストケース一覧)へ反映する。述語の統合・参照方式の変更のように
   「ついでに満たしていた条件」が計画に書かれないまま消える形も同じ手順で見る。
   `plan-reviewer` に渡してから指摘される形が繰り返され、すり抜けは 0(毎回レビューで捕まる)
   なのに計画の書き直しが繰り返されたため、レビューへ渡す前に確かめる位置へ前倒しした
   (`分類: plan-implicit-condition`)
8. **ファイル表が固まったら、同じファイルを触る open の PR を引き、重なりと、引いたコマンド・件数を
   計画に書く。** `gh api 'repos/{owner}/{repo}/pulls?state=open&per_page=100' --paginate --jq '.[].number'` で
   番号を引き、各番号について `gh api 'repos/{owner}/{repo}/pulls/<番号>/files?per_page=100' --paginate --jq '.[].filename'`
   をファイル表と突き合わせる。重なりがあれば、どちらが先に入る前提かを書く。手順 1〜7 で
   ファイル表が増えるので最後に踏む。実例は
   `harness/case-law/process.md`「`なし` から切り出した形 — 計画のとき、同じファイルを触る open の PR を数えていなかった」

## フェーズ 4: 計画の検証(`plan-reviewer`)

計画を Issue に書いたら、**実装に入る前に** `plan-reviewer` サブエージェントへ渡す。

```text
ゴール: <ゴール>
種類: <`flow:*` のラベル>
計画: <変更するファイルと置くもの / テストケースの一覧 / 却下した案とその理由 / 未決の判断>
```

指摘は握りつぶさない。**受け入れるなら前回の計画・採用した指摘・種類を `planner` に渡して直させ、
受け入れないなら理由を Issue に書く。**
どちらも書かずに実装へ進まない。指摘が計画の前提(ゴール)を揺らしているならフェーズ 1 へ戻る。

## フェーズ 5: 実装

**`implementer` を前面で単独で起動する**(同じメッセージに他のツール呼び出しを並べない。理由は
「サブエージェントの使い方」)。渡すもの:

```text
ゴール: <ゴール>
Issue: #<番号>
種類: <`flow:*` のラベル>
工程: <`flow:feature` は 仕様の固定 / 仕様の実現、`flow:bugfix` は 再現テスト / 修正、`flow:refactor` は 現状の固定 / リファクタ。この 3 つのときだけ>
計画: <plan-reviewer を通した計画と却下案>
```

- 実装の手順は `.claude/agents/implementer.md` が持つ
- **`flow:feature` / `flow:bugfix` / `flow:refactor` では `implementer` を 2 つの工程に分けて起動する。**
  `implementer` は commit しないので、1 回で書かせると第 1 工程の分だけが先に入ったコミットが作れない。
  工程ごとに何を書かせ、何を確かめるかは種類のファイルのフェーズ 5 が持つ
  - **第 1 工程は、種類のファイルのフェーズ 5 が第 1 工程に書かせるとしたものだけを書かせる。** 返ってきたら
    「サブエージェントの使い方」の `git status --porcelain` の突き合わせを、計画のファイル表で第 1 工程に
    挙げたファイルだけに狭める。種類のファイルの確かめ方で合格したら commit する。これが
    **第 1 工程のコミット**で、第 2 工程以降はこれと比べる
  - **第 1 工程に書くものが無いなら、第 1 工程を省く。** 第 2 工程を起動する前の HEAD を第 1 工程のコミットの
    代わりとして Issue に書く(どの場合に無いかは種類のファイル)
  - **第 2 工程で実装を変えさせる。** フェーズ 6・7 の直しも第 2 工程の値で渡す
  - **第 2 工程から返ったら(`flow:feature` / `flow:bugfix`)、親が次を走らせて終了コードが 0 であることを
    確かめる。** フェーズ 5 の第 2 工程に限る。フェーズ 6・7 の直しのたびに何を確かめるかは、種類のファイルの
    フェーズ 6 が持つ

    ```bash
    git diff --exit-code <第 1 工程のコミット> -- <第 1 工程のテストのファイル>
    ```

- **`implementer` が計画から外れて止めて返ってきたら、** 親が外れた理由を Issue に追記してから、
  続けるかを決めて起動し直す。後でまとめて書くと理由が思い出せなくなる
- **Issue・PR 本文に事実の主張を書いたら、書き終えるたびに親が `claim-verification` スキルで
  確かめる**(フェーズ6まで持ち越さない。`.claude/skills/claim-verification/`)

## フェーズ 6: 実装の検証(`implementation-reviewer`)

実装が一通り終わったら差分を `implementation-reviewer` サブエージェントへ渡す。**単独で、前面で
起動する**(同じメッセージに他のツール呼び出しを並べない)。実装を壊して確かめるので、背景に
なると(前面で起動して約 120 秒で移された場合を含む)git 操作の抑止が効かない(「サブエージェントの使い方」)。

```text
ゴール: <ゴール>
差分: <git diff の出力、または変更したファイルのパス一覧>
```

この位置に置くのは、過剰な防御が PR に出た後だと差分の意図と絡んで剥がしにくくなるため。

返ってきた指摘の採否を決め、採用したものを種類(と工程)と一緒に `implementer` に渡して直させる。
採らないものは理由を Issue に書く。

## フェーズ 7: PR

- **PR を出す前に、フェーズ 1「種類の確定」の 1 のコマンドでラベルを読み直す。** 変わっていたら
  フェーズ 1 へ戻る(同じ節の 6)
- **PR 本文は `pull-request` スキルで書く。** 意思決定の書き方は `.claude/.pr-template.yml` の
  `decision_record` に従い、材料にはコミット本文に加えて Issue の計画・却下案を使う(Issue からは
  省かない → `rules/process.md`「実装の進め方」)
- **本文に `Closes #<Issue 番号>` を書く**(`rules/process.md`「着手した Issue は、その回で閉じる」)。
  `.github/workflows/pr-closing-issue.yml` が、閉じる Issue を持たない PR を落とす
- CI を通す(いまは `pr-closing-issue` のみ)。push 前の検査や CI が落ちたら、直しは
  種類(と工程)と一緒に `implementer` に渡す(判断を伴わない自動修正コマンドだけは親が走らせてよい →「役割の分担」)

**push の前に、まずフックが発火する環境かを確かめ、続けて CI と同じ検査を 1 つずつ
独立に実行して結果を確認する。**

```bash
echo hook-canary          # 必ず deny されるカナリア(.claude/hooks/hook-canary.sh)
```

```bash
bash harness/githooks/pre-push    # push 前検査ひとまとめ(構文 / shellcheck / 判定表)
```

- **`pre-push` が呼ぶものは 1 つずつ独立に走らせてもよい。** 中身は
  `harness/githooks/README.md`「何が走るか」。`&&` で連ねると途中の出力が流れて
  末尾しか見えないので、失敗を読むときは 1 つずつに戻す
- **このリポジトリにはまだ型チェック・lint・テストが無い。** アプリケーションのソースが
  入ったら、その言語の検査を `harness/githooks/pre-push` と `.github/workflows/` へ足し、
  **同じ差分でこの一覧も直す**(`分類: harness-process-drift`。検査を足して手順書へ
  反映しないと、次にその検査へ触れる人は CI が落ちて初めて存在を知る)
- **カナリアが通っても、それだけでは不発と決まらない。** カナリアは自分の取りこぼしと本当の
  不発を区別できない。`.claude/hooks/README.md`「発火しているかを確かめる(カナリア)」の表で
  PreToolUse の痕跡を見て切り分ける。`分類: hook-environment` を付けてよいのは痕跡が無い枝だけ
- **不発と分かったら**、その旨を PR 本文と記録に残す。ゲートは git hooks と CI にあるので、
  通ってしまっても以降の手順は変わらない
- **不発と分かったら、このセッションで禁止コマンドを既に実行していないかも見直す**
  (取りこぼしの枝では要らない。フックは発火しているので止まっているはず)。
  `block-run-without-install.sh` / `git add -A` の抑止など、**セッション中の行為そのものを
  止める**フックは git hooks(層 2)・CI(層 1)に移せず
  (`.claude/hooks/README.md`「カバー範囲と残る穴」)、不発環境ではこの層でしか止まらない。
  Bash の実行履歴を見直し、該当があれば取り消す
  (`git add -A` を打ってしまったら `git reset` して個別に add し直す)
- **`&&` で 1 本に連ねない。** 連ねると途中の出力が流れて末尾しか見えず、「全部通った」と
  読み違える(実際に 2 回、format 差分のまま push して CI を落としている)。**カナリアを
  混ぜた場合はさらに、deny でコマンド全体が止まり、後ろの検査が 1 つも走らない**
- **フックは保険ではなく確認。** push 前検査の enforcement は git hooks(`harness/githooks/`)が
  担う。`.claude/hooks/` に置くのは、同じスクリプトを編集中に走らせる即時フィードバック層
  (いまこのリポジトリには置いていない)

## フェーズ 8: マージ後の追記

マージされたら次の 3 つを行う(マージは `.claude/hooks/post-merge-review.sh` が検知して提示する)。

1. **意思決定が変わったところがあれば、該当 Issue にコメントする**(計画では A に置くとしたが
   レビューで B に移した / 却下していた案を採用した / ゴールの範囲が変わった)。
   変わっていないなら書かない。**Issue は `Closes` で閉じているが、閉じたままコメントは残せる。
   開け直さない**
2. **続きの作業が要るものは、新しい Issue を立てて元の Issue からリンクする**
   (`rules/process.md`「着手した Issue は、その回で閉じる」)。スコープ外にしたもの・
   決定が変わって作り直しになったものが該当する。種類はフェーズ 1「種類の確定」の 4 で決める
3. **`harness-record` スキルでその回の評価を記録する**。記録を残すところまでで、集計と規約の
   見直しは行わない(→ `harness-growth`)

## サブエージェントの使い方

- **検証は必ず別のエージェントに投げる。** 自分で書いた計画を自分で検証しても同じ前提のまま
  読むので、抜けが同じ位置に残る
- 検証エージェントに実装させない。指摘だけを返させ、直すかどうかはこちらで判断する。
  直すのは `implementer` で、検証エージェントとは別に起動する
- **`implementer` から返ったら、`git status --porcelain` を「計画のファイル表と、渡した指摘の対象」と
  突き合わせる。** 一致したら commit して、それを作業ツリーの基準にする(push はフェーズ 7)。
  2 つの工程に分ける種類の第 1 工程は、フェーズ 5 が突き合わせる範囲を狭める
- **implementation-flow の中のコミットの区切りはこの手順(工程と、`implementer` から返るたび)が決め、
  `commit` スキルの分割ルールより優先する。** 件名と本文の書き方は `commit` スキルに従う
- **それ以外のエージェントから返ったら、指摘を読む前に作業ツリーが基準のまま
  (`git status --porcelain` が空)かを見る**(`分類: subagent-control`)。エージェント定義に
  「変更するな」と書いても書き換えることがある。戻さずに指摘へ対応すると、`implementer` の変更と
  エージェントの書き換えが混ざってコミットに載る
- **直しは `SendMessage` で続けず、新しい Agent 呼び出しで `implementer` に渡す。** 実行中の印を
  作るフックの matcher は `Task|Agent` で、`SendMessage` には当たらない(`.claude/settings.json`)
- **作業ツリーを書き換えるサブエージェントは単独で前面で起動し、完了の結果を受け取るまで
  git add / commit / push を挟まない**(同じメッセージに他のツール呼び出しを並べない)。
  ミューテーション実測や実装の途中でコミットすると、その瞬間の書き換えが載る(pr-391 #18)。
  `block-git-during-verification-agent.sh` が実行中の印がある間の git 操作を機械的に止めるが
  (対象は `.claude/hooks/README.md`)、印が残るのは前面にある間だけ。
  `run_in_background: true` を明示した起動は `track-verification-agent-activity.sh` が拒否するが、
  前面で起動しても、実測した実行環境では 120 秒を超えた起動は約 120 秒で背景へ移され、移された後は
  印が無い(フックの冒頭)。
  単独で起動するのは、移された後に並べた呼び出しが実行中に走りうるため。
  実測の記録は `harness/case-law/process.md`
- **バックグラウンドになった場合は、完了を取り逃さない**(前面で起動して約 120 秒で移された
  場合を含む)。結果を受け取るまで次のフェーズへ進まない
- **セッションの途中で `.claude/agents/` に足した定義は、同じセッションから呼べないことがある**
  (リモート実行環境で `Agent type not found` を実測。呼べた回もある)。そのときは `general-purpose` に
  定義ファイルを読ませて代行させ、定義の `tools` に無いツールを使わないことを prompt に書く。
  代行中は印も作られないので、作業ツリーを書き換えるサブエージェントは前面で単独で起動し、
  完了を受け取るまで git add / commit / push を挟まない
