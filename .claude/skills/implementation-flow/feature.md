# `flow:feature`: 仕様を落ちるテストで固定してから実現する

`flow:feature` の Issue で、`SKILL.md` の各フェーズに**足す**手順。書いていないフェーズは
`SKILL.md` のまま。

**実装より先に、assert で落ちるテストと骨組みを書いてコミットする。** 実装と同時に書いたテストは、
実装に合わせて書かれていないかを確かめられない。`implementation-reviewer` のミューテーションが
示すのは判断ごとに落ちるかで、テストが仕様から先に書かれたかではない。

このリポジトリのテストは判定表(`*-cases.sh`)。ソースを持つ取り込み側は、その言語のテストランナーで
同じ手順を踏み、下の「認める形」の表にそのランナーの行を足して使う。

## フェーズ 3: 計画に足すもの

- **ファイル表に工程の列**(`仕様の固定` / `仕様の実現`)を付ける。第 1 工程に置くのは次のもの
  - テスト: 判定表のケースとその共有物(取り込み側ではテストの置き場とその共有物)
  - 骨組み: 第 1 工程で足す公開 API のシグネチャと仮の戻り値。新しい関数・スクリプト、列挙・分岐に
    足す枝(何もしない枝)、引数・出力に足す項目を含む
  - 型・読み込みを通すために要る、呼び出し側の機械的な書き換え(`SKILL.md` フェーズ 3 の手順 1 で数えたもの)
  - 判定表を新設するなら、その配線(`harness/githooks/pre-push` への追加)
- 既存テストの期待値を変えるときは、第 1 工程で書き換えて RED(失敗の 1 行目が下の「認める形」に
  入る落ち方)に数える
- 第 2 工程に置くのは実装
- **RED 表。** 別の表ではなく、計画の「テストケースの一覧」に列を足したもの。各行に、テスト名 /
  骨組みの仮の戻り値 / 期待値 / 第 1 工程での結果(RED か、骨組みで通るか)/ 予想する失敗の 1 行目 を
  書く。行は第 2 工程で通す順(単純なものから)に並べる。三角測量(同じ公開 API に別の入力で足すテスト)も
  ここに載せる
- **予想する失敗の 1 行目として書ける形**(これ以外は assert に届いていない)

  | 対象 | 認める形 |
  | --- | --- |
  | 判定表 | `NG   expected=<期待> got=<実際>  <ケース名>`(`got=error(…)` は除く) / 予告した `NG   検出器の種別が docstring の一覧と食い違う(…)` / 予告した `NG   <種別> を期待するケースが表に無い`(後の 2 つは種別を照合する判定表で、骨組みの検出器と docstring・表の種別が揃っていないと出る) |
  | 取り込み側のテストランナー | assert の失敗(期待値と実際の値の食い違い)と、予告した「不在・失敗の値を取り出そうとして落ちた」失敗 |

  認めない形: `got=error(…)`(フックが 0 以外で終わった・JSON が壊れた)、読み込み・import の失敗、
  コンパイルエラー、「未実装」を表す失敗(`todo!()` など)
- **仮の戻り値の作り方**
  - 期待値と違う値を選ぶ(`rules/testing.md`「assert は『落ちうるか』と『1つの仕様か』で見る」)
  - 成功・在りの形で期待値と違う値を作れるならそちらにする(assert まで届くため)
  - 作れないときだけ失敗・不在を返し、RED 表に取り出しの失敗を予告して、どの呼び出しで取り出すかを書く
  - 例外・「未実装」で落とさない(assert の失敗と区別できない)
  - 判定表を持つフック・スクリプトの骨組みは「何も出さず exit 0」にする(`NG expected=deny got=pass` で
    落ちる。スクリプトが無いと `got=error(exit=127)` で、認めない形になる)
- 骨組みのままで通るテストは、理由を付けて RED 表に載せる。同じ公開 API に RED のテストが 1 件以上
  あるときだけ認める
- 型のテストは RED の対象外(シグネチャ自体が骨組みで、第 1 工程の型検査で通る)
- **第 1 工程を省く条件:** 自動テストで落とせるものが無い場合(doc・設定だけ、判定表を持たない
  スクリプト)。省くときは理由と代わりの確かめ方を書く。一部だけ当たるなら、その部分を第 1 工程に
  置かず理由を書く
- 既存の振る舞いの誤りを直す作業(拠り所が既存の設計ドキュメント・`rules/`・テストにある)は
  `flow:bugfix`、振る舞いを変えない作業は `flow:refactor`。`flow:feature` に合わない作業なので、
  計画せずに止め、`SKILL.md` フェーズ 1「種類の確定」の 6 に従う

## フェーズ 5: 工程ごとに書かせるものと確かめること

2 つの工程に分ける仕組み(工程の渡し方・第 1 工程のコミット・第 1 工程を省くとき)は `SKILL.md` フェーズ 5。

1. **第 1 工程(`工程: 仕様の固定`): ファイル表で第 1 工程にしたものだけを書かせる。** 返ってきたら、
   親が commit の前に自分で次を走らせ、出力を RED 表と目で突き合わせる(`implementer` の申告で済ませない)
   - 判定表: `bash <表> | grep '^NG'` が、RED 表で RED とした行だけを出すこと。各行が「認める形」に入ること
   - push 前検査: `bash harness/githooks/pre-push`
     - 判定表のケースを RED にしていない回は exit 0
     - RED にした回(新設した表を配線した・既存の表へケースを足した)は exit が 0 以外で、止まった見出しが
       その表であること。`pre-push` は最初に落ちた検査で止まるので、それより後ろに並ぶ検査
       (`harness/githooks/README.md`「何が走るか」)は 1 つずつ走らせて exit 0 を確かめる
   - 取り込み側のテストランナー: 落ちたテストの集合が RED 表の RED の集合と一致し、各 1 行目が
     「認める形」に入ること。ファイル単位の失敗(読み込みの失敗)が出ていないこと
   - 外れたら計画へ戻す。合格したら commit し、これを第 1 工程のコミットにする
2. **第 2 工程(`工程: 仕様の実現`): RED 表の順に 1 件ずつ通させる。** `implementer` は各テストで次を回す
   1. そのテストを走らせて落ちることを確かめ、失敗の 1 行目を控える。判定表はケースを 1 件だけ
      走らせられないので、表を走らせてそのケース名の行を見る。テストランナーで 1 件だけ走らせるなら、
      走ったのがちょうど 1 件であることも確かめる(名前が当たらないと 0 件のまま exit 0 になり、
      「先に通った」と取り違えるため)
   2. 通る最小の実装を書き、同じコマンドで通ることを確かめて次へ進む
   3. サイクルの前に既に通っていたら「先に通った」と控える

   - 返させるもの: サイクルごとのテスト名・コマンド・実装前の失敗の 1 行目(または「先に通った」)・
     触ったファイル・通ったこと。最後に `SKILL.md` フェーズ 7 の push 前検査の終了コード
   - 第 1 工程のテストと骨組みのシグネチャは変えさせない。変える必要が出たら止めて返させる。テストを
     足すのも計画外とする
   - 返ってきたら、親が次を確かめる
     - (a) `SKILL.md` フェーズ 5 の `git diff --exit-code`
     - (b) commit した後に `refactor.md`「書き換えない範囲」の 2 つのコマンド。1 つ目の出力は空、
       2 つ目も空。`refactor.md` の「してよいこと」(移動・改名)は `flow:feature` には当てはめない
     - (c) テスト名の集合が一致すること: 「サイクルで RED→GREEN にしたもの」∪「先に通ったと申告したもの」
       = RED 表の RED の集合で、過不足も重複も無い
     - (d) 各サイクルの実装前の 1 行目が「認める形」に入ること。値は見ない(前のサイクルで変わるため)
     - (e) 返ってきた push 前検査が exit 0
     - (f) `git diff <第 1 工程のコミット> -- <骨組みのファイル>` を読み、骨組みのシグネチャが変わって
       いないこと
   - (c)(d) は `implementer` の申告を見るだけで、RED→GREEN を実際に回したかまでは確かめられない。
     機械的な拠り所は、親が自分で出力を取った第 1 工程のコミット
   - 外れたら、その行を指摘として `implementer` に戻す。先に通ったテストがあれば Issue に書く

**第 1 工程を省いたとき**(フェーズ 3 で自動テストで落とせるものが無いとした)は、`implementer` に
`工程: 仕様の実現` を渡し、サイクルの記録は求めない。代わりに、計画に書いた代わりの確かめ方を
行わせてその結果を返させ、親が Issue に書く。

## フェーズ 6: 直しでは第 1 工程のテストを変えない

- 指摘に応えてテストを足すのはよい(同じファイルでもよい)。第 1 工程のテストを書き換える・消す・
  skip するのはしない
- 直させるたびに、親が次を確かめる
  - commit した後に `git diff --numstat <第 1 工程のコミット> HEAD -- <第 1 工程のテストのファイル>` の
    削除列がすべて 0(commit の前に走らせると HEAD との比較なので直しが入らない)
  - `refactor.md`「書き換えない範囲」の 2 つのコマンド。1 つ目は、テストへの追加行がまるごと新しい
    テスト(判定表なら新しい行)で、既存テストの本文の中への追加ではないことを目で確かめる。2 つ目は空
- **`implementation-reviewer` のミューテーションはそのまま行わせる。**

## フェーズ 7: PR 本文に 2 つの工程のコミットと RED の出力

PR 本文に、**第 1 工程のコミット**と第 2 工程以降のコミットを並べて書く。あわせて、第 1 工程で
親が取った出力(判定表の `grep '^NG'`、取り込み側ならテストランナーの失敗の一覧)を添え、マージ後も
RED を辿れるようにする。第 1 工程を省いたなら、その理由と代わりの確かめ方の結果を書く。
