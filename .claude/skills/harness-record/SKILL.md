# 記録を残す

マージされた PR 1 本につき、記録を 1 ファイル残す。記録は「今回何に躓いたか」を
分類タグ付きで書いたもの。溜まると `AGENTS.md`「ルールに書かれていない指摘が 2 回以上
出たら規約の抜けとして扱う」を機械的に数えられるようになる。

**記録は実装者への評点ではない。** 「良い / 悪い」ではなく「何が起きて、次にどう防ぐか」を書く。

**このスキルの管轄は記録を 1 ファイル足して PR にするところまで。** 集計・介入の判断・
`rules/` やフック・スキルの変更は行わない(→ `harness-growth`)。境界の理由は末尾の
「ここで終わる理由」にある。

---

## Step 1: 材料を集める

対象 PR について次を集める。

| 材料 | 取り方 |
| --- | --- |
| レビュー指摘(人) | `pull_request_read` の 3 つを**すべて**引く(次節) |
| レビュー指摘(サブエージェント) | `plan-reviewer` / `implementation-reviewer` の返答。このセッションの履歴 |
| CI の失敗 | `pull_request_read`(`get_check_runs`)、詳細は `get_job_logs` |
| 差分の規模 | `pull_request_read`(`get_files`) |
| 関連 Issue | PR 本文のリンク。Issue のコメント履歴に計画と却下案がある |
| 実装中の手戻り | このセッションの履歴。計画から外れた箇所、書き直した箇所 |
| フックの発火 | セッション中に hooks が止めた操作(lint 抑制・push ブロックなど) |
| スキル・サブエージェントの発火 | **発火ログ**(`record-firings.sh` が書く。読み方は下記) |

### 人のレビューは 3 つ引かないと落ちる

**`get_review_comments` だけでは足りない。** GitHub は人のレビューを 3 つの別の場所へ
置くので、`pull_request_read` を 3 回引いて合算する。

| メソッド | そこにしか無いもの |
| --- | --- |
| `get_review_comments` | 行に紐づくレビューコメント(スレッド) |
| `get_reviews` | **レビュー本文**。行に紐づかない一言はここにしか出ない |
| `get_comments` | PR 全体へのコメント |

**実測(この 3 つが互いを代替しない証拠):**

- PR #301 は `get_review_comments` が 0 件だが、`get_reviews` に
  「pane-bodyにストーリーがないよ」がある(記録 pr-301#16 はこれ)
- PR #221 / #240 は逆に `get_reviews` の本文が空で、中身は
  `get_review_comments` のスレッド側にある

片方だけを引くと「レビュー指摘は無かった」と誤って結論する。**0 件だったときこそ
3 つとも引いたかを確かめる。**

`get_comments` は CI レポート・Storybook プレビューなど bot の投稿が大半を占める。
**`user.login` を見て人と bot を分ける**(`github-actions[bot]` 等は指摘ではない)。

### セッション中に受けた指示も「人のレビュー」

GitHub に残らない口頭の指示(「その UI はやめて欲しい」など)も、サブエージェントが
捕まえられなかった指摘であることに変わりはない。**`レビュー（人）` として記録する。**
PR #317 の「ボタンで入れ替えるのはダサイ」はこの形(記録 pr-317#46)。

### スキル・サブエージェントの発火はログから取る

`.claude/hooks/record-firings.sh` が発火の瞬間に
`${TMPDIR:-/tmp}/agent-harness-firings-<session_id>.log` へ 1 行ずつ書き出している
(1 列目 = 時刻、2 列目 = `session` / `skill` / `agent`、3 列目 = 名前)。
**記憶(自己申告)からではなく、このログを読んで記録の「発火」に書く。**

```bash
ls "${TMPDIR:-/tmp}"/agent-harness-firings-*.log
```

読み方は先頭の `session` 行(セッション見出し)で決まる。

| ログの状態 | 記録に書くこと(書式は崩さない — `count.sh --shrink` が数える) |
| --- | --- |
| 見出しがあり、発火行もある | ``- 発火: `<名前>` <回数>回``(1 行 1 装置) |
| 見出しがあり、発火行が無い | `- 発火: 無し`(**本当に起動していない** — それ自体が指摘の材料) |
| 見出しが無い / ファイルが無い | `- 発火: 計測対象外(フック不発)`。「未使用」と結論しない |

見出しを先に書くのは、フックがフェイルオープンかつサイレントなため。見出しが無い
ログでは「起動しなかった」と「フックが発火しなかった」を区別できない。

**手戻りとフックの発火(止めた操作)は記憶からしか取れない。** 別セッションで実行する場合は
Issue と PR に残っている記録から復元し、復元できない分は「不明」と書く。発火ログも
別セッションの分は残っていないことがある(tmp はセッションと同じ寿命)。
**推測で埋めない**(埋めると記録が推測混じりになり、回数の根拠として使えなくなる)。

## Step 2: 記録を書く

`harness/records/pr-<番号>.md` に
[templates/record.md](templates/record.md) の形式で書く。
**`.claude/` の下には置かない**(書き込みのたびに承認が要るため /
[`harness/records/README.md`](../../../harness/records/README.md))。

- **指摘 1 件 = 1 ブロック。** まとめて 1 件にしない(分類が混ざって数えられなくなる)
- `分類` は [templates/record.md](templates/record.md)「分類の語彙」から選ぶ。
  **語彙を勝手に増やさない**(増やせるのは `harness-growth` の棚卸しだけ)
- `出どころ` は [templates/record.md](templates/record.md)「出どころの語彙」から
  **ちょうど 1 つ**選ぶ。**括弧の中に自由記述を足さない**(「2 巡目」「ミューテーション実測」
  などは「内容」に書く)。`レビュー（人）` / `レビュー（bot）` は
  **サブエージェントがすり抜けた証拠**として `count.sh` が別に数えるので、
  サブエージェント由来と同じ綴りにしない
- どれにも当てはまらないなら `分類: なし` と書き、内容に何の話かを書く。
  これが「規約の抜け」の候補になる
- **指摘が 0 件の回も記録を残す。** 0 件は「順調だった」というデータ

### `対策済` の行は書かない

テンプレート末尾の `対策済:` は **`harness-growth` が介入したときにだけ書く行**で、
`count.sh` はこれを「ここから数え直す」の起点として読む。介入していない回に書くと
再発数が 0 に戻り、次に数える人が誤った判断をする。`見送り:` の行も同様に
`harness-growth` だけが書く(縮める候補の見送りの印)。

介入が無い回は「規約への反映」に**無しとその理由**を書いて終える。

## Step 3: 記録の PR を出す

- **記録対象の PR とは別のブランチを切る**(記録対象はすでにマージ済み)
- PR 本文には、記録した分類の一覧を書く
- **指摘が 0 件の回でも PR は出す。** 記録が残ること自体が目的
- `rules/` ・フック・スキルには触れない。差分は `harness/records/` の 1 ファイルだけになる
- **記録 PR は Issue を持たない。** 判断を残す回ではないので立てず、本文に `Closes` も書かない
  (`AGENTS.md`「着手した Issue は、その回で閉じる」の例外)。**この例外は「`harness/records/`
  配下の新規 1 ファイルだけ」という上の形でだけ成立する** — 検査(`.github/scripts/
  check-pr-closing-issue.sh`)がそれを条件にしているので、2 ファイル目が要るようになったら
  検査の条件も一緒に直す

## ここで終わる理由

集計から先を同じスキルに置くと、「記録だけ残して」と指示しても後続の手順まで実行される
(実測済み)。**制限を指示ではなくファイル境界で行うための分割**なので、ここに Step を
足さない。数える・介入する必要があると気づいたときも、このスキルの中では行わず
`harness-growth` へ回す。

## 注意事項

- **過去の記録を書き換えない。** 判断が変わったら新しい記録に書く。
  書き換えると履歴が消えて回数を数えられなくなる
- 記録は PR ごとに 1 ファイル。1 つのファイルへ追記する形にしない
  (並行する PR が必ず衝突する)
- 記録を書くために実装を蒸し返さない。集めるのは**すでに出ている**指摘・失敗・手戻りだけ
